# Redis RDB、AOF 与恢复验证

RDB 保存时间点快照，AOF 记录可重放的写操作。持久化降低数据丢失风险，但不代替异机备份、恢复演练和故障容量规划。

## 方案与取舍

| 方案         | 特性                     | 主要代价                                           |
| ------------ | ------------------------ | -------------------------------------------------- |
| RDB          | 紧凑快照，便于备份       | 两次快照之间的数据可能丢失；fork 有停顿与内存开销  |
| AOF everysec | 通常约每秒同步           | 故障时仍可能丢失最近写入，极端条件不能承诺固定窗口 |
| AOF always   | 每次写入同步，耐久性更强 | 更高磁盘延迟与吞吐成本                             |
| 两者并用     | 同时保留快照与日志       | 更多存储和运维复杂度                               |

## 运维要点

使用 BGSAVE/BGREWRITEAOF 前评估 fork 和写时复制内存。检查 INFO persistence、磁盘容量和最近保存状态。复制、持久化和备份是不同保护层；复制还可能传播误删。

恢复前保留原文件副本，在隔离环境验证可加载、数据完整、版本兼容与业务校验。不能直接删除损坏日志后宣称恢复成功。

### 版本变化与兼容

| 版本     | 变化                                          | 方案                                                 |
| -------- | --------------------------------------------- | ---------------------------------------------------- |
| 7.0 前   | 常见单文件 AOF 布局                           | 备份应与该版本重写行为匹配                           |
| 7.0+     | 多部件 AOF，包含基础文件、增量文件与 manifest | 按完整目录/清单一致性备份，不只复制旧 appendonly.aof |
| 同时启用 | 正常启动优先使用 AOF 恢复                     | 不手动混合不同时间点的 RDB/AOF；按官方恢复步骤操作   |
